# Table design internal to `its-log`

Date: 2026-01-16

## Status

Accepted

## Context

In an event logger, the table design is implied by the logging philosophy. This ADR documents both.

## Logging philosophy

The `its-log` logger enables three *kinds* of logging activities:

1. **Event clusters**. A cluster of events is two or more events that are related. The nature of their relationship is not defined; what a cluster defines is a *set* of events.
2. **Event categories**. Events belong to categories, or sources. For example, if an application has a `frontend` and a `backend`, then we might place all events into one of those two categories. It is then possible to ask analytical questions about how many events took place in (say) the `backend` category.
3. **Event uniqueness**. An event might carry a value. An event value is assumed to have the property of *uniqueness*, and attempts to analyze value data categorically will fail. An example would be a `backend` source that logs an (anonymized) user identifier as a value associated with the event. We could then ask questions about how many unique users used the backend.

An `its-log` event supports the recording of an optional cluster, one mandatory category, one optional category, and supports the recording of a unique, optional value. 

## Logging semantics and analysis

By being explicit/opinionated about the nature of each event, it becomes possible to write generalized ETL steps to process events. For all applications that use `its-log`, we can always do baseline processing, counting events by cluster, category, combination of category, or unique values within categories.

### Clusters 

Clusters are difficult to automate, as they are a "cluster of (possibly) unrelated events." We can count how many unique clusters were recorded, the mean and median number of events per cluster, the largest and smallest clusters, and so on. If the clusters are very deterministic (e.g. we have two clusters in our application, and each always has three events in it) then these numbers are largely uninteresting.

Clusters are more useful for customizing analysis: how many times do category A and B appear in clusters together? This becomes application-specific interms of what the meanings of the events and categorise are. For this reason, `its-log` does no automatic processing of clusters.

### Counts of events by mandatory category

Because every event must, at least, have a category, it is possible to have a default analysis step applied to all applications that counts how many events were in each category. If the application logs to 5 different categories, we can count the events in those five different categories, even if we do not know what the categories are.

### Counts of events by heirarchical category

Because every event has an optional second category, we can automate multi-level counts. If we log events like `<A, X>`, `<A, X>`, `<A, Y>`, `<B, X>`, `<B, Z>`, we can produce a summary table that looks like

| C1  | C2  | count |
| --- | --- | ----- |
| A   | _   | 2     |
| A   | X   | 1     |
| A   | Y   | 1     |
| B   | _   | 2     |
| B   | X   | 1     |
| B   | Z   | 1     |
| _   | X   | 2     |
| _   | Y   | 1     |
| _   | Z   | 1     |

`its-log` makes no assumptions about the relationship between C1 and C2; therefore, we count the incidence of C1, C2, and (C1, C2) automatically. Whether they are used or are meaningful is not relevant *yet*.

### Counts of unique events

Using the above example, we can imagine an log that captures an API version (C1 = `v1`, `v2`, `v3`, etc.), and C2 captures the API endpoint (`/profile`, `/photo`, etc.). A *value* would be a unique identifier associated with an event. For example, we might salt and hash a username (preserving privacy), and record it with each API authenticated API call. In this way, we would record events like `<v1, /photo, "a3ef">`, `<v1, /photo, "bb61">`, `<v2, /profile, "a3ef">` and so on. Now, we can continue to do automatic analyses of the categorical data, *and* we can count how many *unique* values appeared for C1 as well as for `(C1, C2)`. 

## Decision

Its log events capture:

| type      | column     | nullable? | default  |
| --------- | ---------- | --------- | -------- |
| id        | api key id | N         | internal |
| timestamp | timestamp  | N         | now()    |
| cluster   | cluster ID | Y         | null     |
| category  | source     | N         | N/A      |
| category  | event      | Y         | null     |
| unique    | value      | Y         | null     |

In this way, ETL processes can be developed for baseline analysis of all applications that use `its-log`. 

## Consequences

`its-log` is intended to serve as a low-cost, high-volume logger for simple, categorical events, easily deployed in containerized environments via infrastructure as code. Its opinionated structure allows for out-of-the-box data transformations, and therefore accelerates some of the sensemaking of application logs. Like all opinionated tools, this structure introduces limitations. That said, `its-log` can be made to serve in many ways as a logger. For example, the `value` column could, in theory, be used to store JSON documents. 

This design is intentional given the kinds of use-cases that drove its development. Therefore, the consequences are that there are some kinds of events that are well-served, some kinds of events that can be easily/categorically analyzed, and others that might require additional thought or, perhaps, a different tool.
