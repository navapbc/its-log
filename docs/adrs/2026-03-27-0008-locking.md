# Locking in `its-log`

Date: 2026-03-26

## Status

Accepted

## Context

`its-log` is built on SQLite for performance, resilience, and architectural simplicity. 

That said, SQLite is a filesystem-based database, and does not like to have multiple writers. This is a problem for an API that is intended to sustain high throughput from multiple writers.

## Locking

Golang has many primitives for parallelism and concurrency control. `its-log` will use the simplest of these: the lock. We will use it in two places to start:

### Flushing buffers

`its-log` receives event API requests, buffers them, and then flushes the buffer under one of two conditions:

1. The buffer is full, or 
2. A pre-determined amount of time has passed

Under normal operation, `its-log` runs with a buffer of length 2000 and a flush wait time of 1 second. (In other words, after 1 second of inactivity, `its-log` flushes the buffer, regardless of how few or many events are present.)

We lock before opening the database to flush events, and unlock when done.

### Running ETL pipelines

It is possible to run a pipeline of ETL actions on `its-log`. Under normal operation, `its-log` writes data to a separate database for each day. For example, it will log data from March 3rd to `app_2026_03_03.sqlite`. As the UTC clock flips to the next day, a new database is created, meaning data is then logged to `app_2026_03_04.sqlite`. In this regard, ETL pipelines are almost certainly going to be run on *the previous day's database*, and therefore, there should never be data being logged to the 3rd when the ETL pipeline is executed. There should be no contention.

"Should," however, is a dangerous game. Therefore, we aquire a lock before launching the ETL pipeline, and defer closing it until after completion. In this regard, *all* ETL steps are run under a single lock. This is necessary, because it is common to have one step do a calculation, and then another step assert correctness. In this way, an ETL pipeline is self-reporting/self-asserting in its correctness.

## Testing

Integrated stress tests have been developed with many parallel writers that continuously write events (with jitter) with a buffer length of 20. After many iterations, the ETL is executed while still under load from parallel writers; locks are created and released, ETLs run successfully, and no logging events are lost. 

Further, it is now possible to open an SQLite database for writing *manually* while under load. Specifically, an application like "SQlite DB Browser" can be used to open the DB file for writing (thus locking it) while `its-log` is attempting to log at a high rate. The buffer fills, the lock blocks writing, and once SQlite Browser releases its lock, `its-log` is able to continue. This will have no relationship to production operation, but it is reassuring that truly parallel access from multiple applications inspire correct behavior for the logger.

## Decision

We will use locking to protect the database during critical operations, preventing SQLite errors regarding concurrent write access.
